# React Native with an Expo development build; FFmpeg fork for export, Skia for preview

The app is React Native with Expo, written in TypeScript throughout, and run as a **development build**. Expo Go can't be used, because it can't load the native modules the app needs.

- **Export** (ADR 0003) runs on the phone through a community fork of FFmpeg-kit. The whole composition becomes one FFmpeg command, generated by a pure function of the resolved composition.
- **Preview** draws with React Native Skia.
- **Looks and overlay fonts** are shared data. Both paths apply the same data, so preview and export are visibly similar. They are not pixel-identical.

This was chosen because it is the fastest route to a working video file on the phone within the 48-hour deadline. It is also the same kind of product Hoopr ships: a native iOS and Android app.

## Considered Options

- **Mobile web / PWA with Canvas + WebCodecs.** Rejected. One compositor could have served both preview and export, so they would match exactly. But encoding support on iOS Safari, keeping large imported files across launches, and memory limits on mid-range Android are each a risk that could sink the project. And a browser tab doesn't feel like Hoopr's product.
- **Bare React Native** (no Expo). Rejected. It gives full native control, but costs time on build setup, permissions, the media picker and saving to the gallery. Expo provides all of those, and a development build still allows custom native modules.
- **Expo Go.** Not possible: it can't load FFmpeg or Skia.
- **Flutter / fully native Kotlin + Swift.** Rejected: a new language and toolchain doesn't fit in 48 hours.
- **Platform media APIs instead of FFmpeg** (Media3 Transformer on Android, AVFoundation on iOS). Rejected for now. They are more robust and hardware-accelerated, but mean two separate native implementations. FFmpeg is one command covering joining clips, turning photos into clips, drawing text, colour adjustments and audio mixing on both platforms.

## Risks

- **FFmpeg-kit is retired.** Its official builds were withdrawn in 2025, so this depends on a community fork that may be unmaintained or incomplete. The fork must include text drawing (`drawtext`, which needs a font library) and an H.264 encoder usable on Android: either libx264 in a GPL build, or the phone's hardware encoder.
- **Nothing native loads until the development build exists.** Neither FFmpeg nor Skia works until the app has been prebuilt and installed on the phone, so the first native build is itself on the critical path.
- **Timebox.** Ticket 01 gets **4 hours**. If there is no successful encode from a development build on the real Android phone by then, we fall back to a **preview-only** app. That fallback must be decided on purpose, during the day, and recorded as a new ADR that replaces the export part of this one and of ADR 0003. It must not be drifted into late at night.
